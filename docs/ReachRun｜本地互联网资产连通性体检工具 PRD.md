## 1. 产品概述

ReachRun 是一款运行在 macOS 本地的个人互联网资产体检工具。

用户首次保存固定域名和境外服务器后，日常只需打开应用并点击“检测全部”。工具先快速判断域名公开网站路径、服务器 SSH 与网站服务是否可用；仅对失败、变化或证据不足的项目自动执行更深的 DNS、IPv4/IPv6、TCP、TLS/SNI 和强制 IP 对照诊断。

产品默认回答三个问题：

1. 哪些资产当前链路可达，哪些需要关注；
2. 与上一个可比较结果相比，哪些是新增异常、已经恢复或持续异常；
3. 异常最可能发生在 DNS、IPv4/IPv6、TCP、TLS/SNI、HTTP 或 SSH 的哪一层，下一步应做什么。

所有检测从当前 Mac 所在网络发起。应用不把域名、服务器清单或检测结果发送到自建服务端，也不在后台定时运行。

## 2. 背景与问题

用户长期持有数十个托管在 Cloudflare 的域名，并购买了若干境外服务器。日常需要快速确认：

- 域名从厦门家庭宽带能否正常解析和访问；
- 是否出现疑似本地解析路径异常、IPv6 异常或 TLS/HTTP 故障；
- 境外服务器的 SSH、HTTP 和 HTTPS 服务是否仍可使用；
- 当前需关注项是刚出现、已经恢复，还是持续存在。

单一远程检测站无法替代本地检测：远程服务反映的是远程机房网络，不代表厦门家庭宽带。纯浏览器页面也无法完成系统解析、原始 DNS、指定 IP + 正确 SNI、SSH identification 等检测。

因此，产品采用“本地检测引擎 + 本地浏览器 UI”架构：浏览器负责交互，本地进程负责真实网络检测。

## 3. 第一性产品目标

### 3.1 核心目标

1. 固定资产清单只配置一次，之后一键完成手动体检。
2. 健康资产优先快速给出结果，不为每个资产默认运行完整取证矩阵。
3. 异常资产自动升级为深度诊断，尽可能缩小故障层级。
4. 默认突出变化和行动，不要求用户阅读原始网络数据才能知道下一步。
5. 原始证据可展开，所有判断均可解释、可降级且不过度归因。
6. 域名与服务器是两类不同资产，但共用一次“检测全部”和统一变化摘要。
7. 应用仅在用户主动打开期间运行，退出后不残留检测进程。

### 3.2 成功标准

- 首次检测后，本地记住域名、服务器配置、最近观测摘要和比较基线摘要；
- 再次打开时，无需重新粘贴即可检测全部资产；
- 健康网络下约 3 秒内出现首批结果；
- 30 个健康域名的快速体检目标约 10 秒完成，最终值由 Phase 0 Spike 实测确定；
- 异常项可以继续诊断，不阻塞健康项展示；
- 结果首页直接显示新增异常、已恢复、持续异常、状态变化和本次无法判断；
- 能区分 DNS、地址族、TCP、TLS/SNI、HTTP 与 SSH 层级；
- 不能安全归因时明确显示“原因未明”或“无法判断”；
- 关闭应用后本地端口关闭，检测任务取消且不残留后台进程。

## 4. 核心领域语言

完整术语定义见仓库根目录 `CONTEXT.md`。PRD 使用以下核心概念：

- **资产**：用户希望长期重复体检的对象，包括域名资产和服务器资产。
- **域名资产**：以稳定 ID 为身份、以 hostname 为关键配置，主要用于检查公开解析与网站访问的资产。
- **服务器资产**：以稳定 ID 为身份，备注名、公网 IP 和预期服务端点均为可编辑属性。
- **服务端点**：服务器上的具体服务，例如 SSH 22、HTTP 80 或 HTTPS 443。
- **公开网站路径**：按照域名正常解析后访问网站的真实用户路径。
- **源站直连**：绕过代理/CDN，强制连接指定服务器 IP，同时保留正确 Host/SNI 的诊断动作。
- **快速体检**：默认执行、优先回答“当前是否可用”的低成本检测。
- **深度诊断**：只对异常、变化或证据不足项执行的进一步对照检测。
- **参考解析**：用于对照的公共 DNS/DoH 结果，不称为“干净解析”或事实真值。
- **最近观测摘要**：最近一次完整“检测全部”中每个资产的粗粒度结果，用于重新打开后的当前展示。
- **比较基线摘要**：每个资产最后一个可比较的有效粗粒度状态，用于判断变化，可能早于最近观测摘要。
- **连通性主结果**：只描述网络与协议链路是否建立，不代替业务健康判断。
- **当前关注状态**：描述本轮结果是否需要用户关注，与连通性主结果分开。

## 5. V1 范围

### 5.1 必须具备

- macOS Apple Silicon 本地运行；
- 固定域名与服务器资产的本地保存、编辑和删除；
- 一键“检测全部”；
- 检测进行中可“停止检测”；
- 域名快速体检与异常自动深度诊断；
- 服务器 SSH、HTTP、HTTPS 服务端点检测；
- 域名与服务器关联后的公网路径自动观察与有限归类；
- IPv4、IPv6 分层结果；
- 新增异常、已恢复、持续异常、状态变化和本次无法比较；
- 关键证据、原因标签、置信度和建议下一步；
- 单项重测、重测待复核项、手动深度诊断；
- 复制诊断摘要；
- loopback、随机会话 token、严格输入和目标地址校验；
- 明确退出与空闲自动退出。

### 5.2 明确不做

- 后台定时检测、菜单栏常驻、通知和告警；
- 长期历史、趋势图、SLA 和数据库；
- 全国多省、多运营商分布式拨测；
- “已被 GFW 阻断”之类确定性结论；
- 境外对照探针或东京 VPS 参与 V1 判定；
- ICMP Ping 和 traceroute 作为默认检测；
- CIDR、端口范围、全端口扫描和通用 UDP 探测；
- 任意 URL、路径、请求头、请求体或代理请求；
- 代理协议、VPN 协议或其他自定义应用协议识别；
- HTTP/3、QUIC 和通用 UDP 服务可用性；
- Cloudflare API 登录、DNS 修改或自动修复；
- 识别 Cloudflare Pages、Workers、Tunnel 等具体产品；
- 多用户、账号、团队协作和云同步；
- Intel Universal、Windows/Linux 图形发行版；
- 面向外部分发的签名、公证和自动更新；
- JSON/Markdown 完整报告导出。

## 6. 目标用户与使用环境

### 6.1 主要用户

- JC；
- 使用 Apple Silicon Mac；
- 常住厦门；
- 固定检查数十个自有域名和若干境外服务器；
- 主动打开应用并点击检测，不需要后台监控；
- 能阅读网络原始信息，但希望默认结果足够直接。

### 6.2 检测环境语义

结果只代表应用运行时的当前网络路径。

应用应展示能够安全取得的环境信息：

- macOS 与应用版本；
- 当前时间；
- 活跃网络接口；
- macOS resolver 配置快照；
- 常见代理环境变量和系统代理迹象；
- 当前是否具有可用 IPv4/IPv6 路径；
- 检测到 VPN/TUN/代理迹象时的置信度提示。

产品不要求用户在检测前完成一长串设置。若检测到可能干扰，仍继续运行并显示：

> 结果代表当前网络路径；检测到代理或 VPN 迹象，部分归因的置信度已降低。

浏览器 Secure DNS 不参与本地 Go 引擎的目标域名解析，因此不作为检测前提。应用只需说明浏览器自身访问路径可能与工具不同。

所有 Web 探测使用同一套显式禁用 HTTP 代理的 Transport，不读取 `HTTP_PROXY`、`HTTPS_PROXY`、`ALL_PROXY` 或系统 HTTP 代理。应用仍展示这些代理迹象；VPN/TUN 等网络层路径无法由应用绕过，因此继续体现在“当前网络路径”中。

## 7. 核心使用流程

### 7.1 首次使用

1. 用户双击启动应用。
2. 程序只绑定 `127.0.0.1` 的随机端口并自动打开浏览器。
3. 用户添加域名资产和服务器资产。
4. 用户点击“检测全部”。
5. 快速体检逐项返回结果。
6. 异常、变化或证据不足项先显示“正在复核”，再自动进入深度诊断，避免尚未复核就闪现红色失败。
7. 页面显示本轮汇总；首次检测标记为“首次检测”，不伪造变化结论。
8. 应用本地保存资产清单、最近一次完整检测时间、最近观测摘要和比较基线摘要。

### 7.2 日常使用

1. 用户打开应用，页面自动加载固定资产、最近观测摘要和比较基线摘要。
2. 首页显示最近一次完整检测时间和“检测全部”。
3. 用户点击一次开始检测；检测期间主按钮切换为“停止检测”。
4. 检测过程中保持列表位置稳定；整批完成后再按“待检测 → 新增异常 → 持续异常 → 本次无法判断 → 状态变化 → 已恢复 → 无变化”排序。
5. 用户可重测单项、重测待复核项或展开深度证据。
6. 用户点击“退出 ReachRun”，服务停止。

### 7.3 意外关闭页面

- 浏览器页面关闭不直接等于应用退出；
- 页面打开期间发送轻量、带 token 的 heartbeat；heartbeat 不包含资产或结果；
- 只有同时满足“没有活动检测”与“超过空闲阈值未收到已认证页面请求或 heartbeat”时，本地进程才自动退出；
- V1 默认空闲退出目标为 10 分钟，最终值由 Spike 验证；
- 用户再次启动时不得产生不可见的重复后台实例，应重新打开现有会话或安全创建新会话。

## 8. 资产管理

### 8.1 通用规则

- 推荐上限：50 个域名资产、20 个服务器资产；
- 资产必须有稳定 ID，重命名不应丢失比较基线；
- 删除资产后立即提供短时“撤销”，避免用阻塞确认框增加日常摩擦；
- 提供“清除全部本地数据”；
- 仅修改备注名不重置比较基线；
- hostname、服务器 IP、SSH 端口、启用的服务类型或主要网站域名等关键配置更改后，该资产下一轮标记为“配置已变更”，不与旧配置强行比较。
- 任一检测运行期间锁定资产编辑；用户可以先“停止检测”再修改；API 在有活动检测时对 `PUT /api/assets` 返回 `409 Conflict`；
- 检测启动时使用不可变资产快照，正式提交前再次校验配置版本，避免旧 IP/端口结果写入新配置。

### 8.2 域名资产

输入层尽可能宽容：

- 支持每行一个域名；
- 支持从 URL、逗号、空格混合文本中提取 hostname；
- 支持 IDN，内部统一转换为 Punycode；
- 自动小写、去重并移除尾部句点；
- URL 中的路径、查询和端口仅用于提取 hostname，不进入检测引擎；
- 拒绝 IP literal、通配符、单标签本地主机名和非法 hostname。

API 和检测引擎只接收规范化 hostname，不接收任意 URL。

### 8.3 服务器资产

每台服务器包含：

- 备注名，例如“东京 VPS”；
- 一个公网 IPv4，可选一个公网 IPv6；
- 是否检查 SSH；
- SSH 端口，默认 `22`，只允许单个合法端口；
- 是否检查网站；
- 一个可选的主要网站域名。

SSH 与网站至少启用一项；两项同时关闭时不允许保存服务器资产。

主要网站域名应优先关联已经保存的域名资产。底层复用同一公开网站探测结果，界面仍分别呈现“域名公开路径”和“服务器服务端点”。

网站服务默认检查：

- HTTP `80`；
- HTTPS `443`。

V1 不支持端口范围或任意服务列表。若网站域名未提供：

- HTTP 可以使用 IP 作为 Host 做有限探测；
- HTTPS 只能确认端口/TLS 是否响应并展示证书；
- 不得声称证书身份或网站配置正确；
- UI 应提示添加主要域名可获得完整 HTTPS 判断。

## 9. 渐进式检测策略

### 9.1 总体原则

快速体检与深度诊断必须分开：

- 快速体检优先回答“服务现在能不能用”；
- 深度诊断回答“失败大致在哪一层”；
- 健康资产不默认执行完整 DNS/协议矩阵；
- 失败项的超时不得阻塞其他资产；
- 所有结果流式展示，不等待整批结束；
- 关键参考服务不可用时局部降级，不把所有资产判为异常。

### 9.2 深度诊断触发条件

至少包括：

- 系统解析整体失败、NXDOMAIN、预期地址集合全部为空，或比较基线中存在的 Web 地址集合消失；
- HTTP fallback 仍无法确认链路、HTTPS/HTTP 行为较比较基线变化，或出现 TLS/证书异常；
- IPv4 与 IPv6 行为不同；
- 域名解析结果与关联服务器 IP 或 Cloudflare 网络类别冲突；
- 已存在有效比较基线，且当前粗粒度状态与其不同；
- 用户手动点击“深度诊断”；
- 关键证据不完整且无法给出安全结论。

单独的 AAAA NODATA 只表示“未配置 IPv6 地址”，不触发深度诊断。HTTP-only 域名首次出现或其规范化地址指纹变化时进入深度诊断；已建立比较基线且地址指纹稳定时，不应每轮重复完整诊断。

新资产没有比较基线这一事实本身不触发深度诊断；首次快速体检只有命中其他失败、冲突或证据不足条件时才升级。

### 9.3 重试原则

- 成功结果不重复探测；
- 超时、连接重置等暂态失败默认再尝试 2 次；
- 明确的连接拒绝、证书错误等确定性结果无需机械重试；
- 重试需有抖动和批次总 deadline；
- 不允许无限重试。

## 10. 域名资产检测

### 10.1 快速体检

每个域名至少执行：

1. macOS 系统解析路径查询 A/AAAA 最终地址；
2. 使用正常系统解析执行 HTTPS `GET /`；
3. 记录实际连接 IP、地址族、TCP/TLS/TTFB/总耗时；
4. 验证证书 hostname、有效期和信任链；
5. 记录有限 HTTP 状态和重定向；
6. HTTPS 不可用时，以 HTTP `80` 做有限补充，区分 HTTP-only 与完全无 Web 服务；HTTP 成功只能证明链路响应，不能验证域名身份；
7. 同时存在 A/AAAA 时，异步验证两个地址族，不阻塞首个“链路可达”结果。

地址族结论必须克制：

- 无 AAAA 时显示“未配置 IPv6 地址”，属于中性事实；
- 本机没有可用 IPv6 路由时显示“当前网络不具备 IPv6 检测条件”，不得判为域名失败；
- 默认访问成功只证明实际选中的地址族可用，不证明 IPv4、IPv6 均健康；
- 每个地址族先对候选 IP 去重，再在受控上限内逐个验证；上限由 Spike 确定；
- 某地址族只有在该族全部候选都已测试且全部失败时，才能显示该地址族失败；
- 同一地址族有成功也有失败时，显示“该地址族部分候选失败”，资产可标为“部分可达”，但不得写成整个 IPv4/IPv6 路径异常；
- 若受控上限导致候选未测完且尚无成功证据，只能显示“证据不足”，不能判该地址族失败；
- `no route`、超时、连接拒绝必须分开记录。

HTTP 请求规则：

- 固定使用根路径 `/`；
- 使用 GET，但限制响应体读取字节数；
- 不上传数据；
- 最多跟随 3 次 HTTP(S) 重定向；
- 每次重定向重新校验目标 hostname 和解析后的公网地址；
- 原 hostname 收到任意合法 HTTP 响应后即证明第一跳可达；后续跳转失败归属于重定向目标，不回算为原 hostname 的 DNS/TCP 失败；
- 若重定向后的用户路径未能完成，域名资产显示“部分可达 · 需关注”，关键证据明确指出失败的重定向目标；
- 不携带用户凭据、自定义 Cookie 或 Authorization；
- 所有 4xx/5xx 都作为独立 HTTP 状态展示，只要 TCP/TLS/HTTP 链路建立即视为网络可达，不得改写成网络不可达；
- 5xx 以及 408、421、425、429、451 进入“需关注”；429 不做紧密机械重试，并尊重合法的 `Retry-After`；
- 401、403、404 和其他未单列的 4xx 在首次出现或状态稳定时默认不判业务故障；若从 2xx/3xx 变化为 4xx，必须作为醒目的“状态变化”进入汇总并触发深度复核。

HTTP-only 域名显示“链路可达 · HTTP-only · 身份未验证”，置信度最高为“中”。首次观测需建立参考解析证据；后续比较指纹对 Cloudflare 等已知动态网络按类别归一化，对其他 HTTP-only 域名保留完整地址集合的本地哈希。指纹发生变化时自动深度复核，但不把地址变化本身直接判为污染。

### 10.2 深度 DNS 诊断

按需执行：

1. 记录 macOS 系统解析结果；
2. 获取当前 resolver 配置快照；
3. 对当前接口公布的 DNS 服务器做受控 UDP 查询；
4. 使用两个独立参考 DoH resolver 查询；
5. 只有在 UDP 截断、异常或需要隔离传输差异时追加 TCP 查询；
6. 默认查询 A/AAAA/CNAME；常规地址集合为空、全部连接失败或与其他证据存在实质冲突时，对原 hostname 追加 HTTPS/SVCB，并处理可识别的 AliasMode 目标；
7. 仍无法取得可用 Web 地址、NXDOMAIN 或委派异常时再查询 NS/SOA 和必要的权威服务器；
8. 记录每项证据的来源、协议、目标 resolver、RCODE、记录、TTL、耗时、超时和可用标志。

不同证据必须分开建模：

- **System Resolution**：应用通过 macOS 系统路径实际得到的地址或错误；
- **Resolver Inventory**：系统当前配置的 resolver 快照，只是配置证据；
- **DNS Observation**：对明确 resolver 发出的原始 UDP/TCP/DoH 查询。

不得声称 resolver 配置快照能证明某次系统查询实际由哪个服务器回答。系统解析若无法暴露 TTL、RCODE 或原始报文，对应字段必须允许缺失。

HTTPS/SVCB 处理边界：

- 从原 hostname 的 HTTPS RR 开始；遇到 AliasMode 后，使用返回该记录的同一个 resolver 对 TargetName 继续查询 HTTPS RR（`HTTPS → HTTPS`），不混用其他 resolver 的结果；
- AliasMode 链结束后，再按最终 ServiceMode/TargetName 解析 A/AAAA；目标没有 HTTPS RR 时按 RFC 9460 的回退语义解析其 A/AAAA；
- AliasMode 只改变连接候选的解析目标；URL hostname、HTTP Host、TLS SNI 和证书身份仍保持原域名；
- 最多跟随 3 层 AliasMode，并检测循环；超限或循环显示“HTTPS/SVCB 解析链无法完成”；
- V1 不把 `ipv4hint`/`ipv6hint` 当成唯一真值，也不完整实现所有 ServiceMode 参数；若只有当前版本不支持的 ServiceMode 才可能找到入口，显示“无法判断 · 当前版本未支持该 HTTPS 服务参数”，不得判为网络失败。

### 10.3 强制候选 IP 对照

当默认访问失败或解析存在实质冲突时：

- 从参考解析中选择候选公网 IP；
- 强制连接候选 IP，但保持原 URL hostname、HTTP Host、TLS SNI 和证书验证；
- IPv4 与 IPv6 必须在同地址族内对照；
- 生成因果归因时，不直接复用可能使用旧连接的快速体检结果；另运行一组“本地候选控制 + 参考候选”的成对复核；
- 成对复核为两侧分别创建全新、禁用代理且禁用连接复用的客户端，并保持地址族、URL、Host、SNI、证书验证、超时、重试与第一跳重定向策略一致；唯一差异只能是拨号 IP；
- 记录实际远端 IP 和失败阶段；
- 一个来源返回多个候选 IP 时不得只测第一个就代表整组；
- 强制对照只把第一跳计入该候选 IP 的证据，重定向后的成功不得反算为第一跳成功；
- 默认路径成功而某个参考候选失败时，连通性主结果仍是“链路可达”，候选失败只进入详情；
- 候选 IP 成功只能证明该候选路径可用，不自动证明另一个结果是污染。
- 无法证明两条路径除目标 IP 外条件等价时，禁止生成“高可信本地解析路径异常”。

## 11. 服务器资产检测

§10.1 的地址族证据规则同样适用于服务器资产：当前 Mac 没有可用 IPv6 路由时，服务器 IPv6 端点显示“当前网络不具备 IPv6 检测条件”，属于未测试而非失败；若 IPv4 服务已响应，不能仅因此把服务器标为“部分可达”。只有本机具备该地址族条件且候选实际失败，才参与部分可达/未建立服务链路判断。

### 11.1 SSH

对启用 SSH 的服务器：

- 连接配置的 `IP:port`；
- 记录 TCP 建连时间和错误类型；
- 发送固定、受限的客户端 identification，接受规范允许的有限前置行，再读取 `SSH-` identification；
- 不继续密钥交换或认证；
- 不读取、上传或使用用户 SSH 密钥；
- identification 合法时显示“SSH 服务响应 · 收到 SSH identification · 未测试登录”；
- TCP 成功但 identification 不合法时显示“端口可达，未确认 SSH”；
- 连接拒绝表示网络路径已到达某个拒绝方，但服务未开放或未监听；
- 超时只显示“当前网络连接超时，原因未明”。

### 11.2 网站探测分流

- 观察到域名直达已登记服务器，或没有主要网站域名时：快速体检服务器 IP 的 `80/443`；
- 观察到域名经 Cloudflare 边缘时：快速体检跳过源站 `80/443`，服务器行展示并复用公开域名结果，只独立检测服务器 SSH；
- 关联关系未确认时：服务器 IP 与公开域名分别检测，明确显示“无法关联”，不得互相覆盖结论；
- Cloudflare 场景的源站 `80/443` 只在用户手动触发“测试源站直连”后执行，结果不进入网站主状态。

Cloudflare 场景必须明确显示“公开网站经 Cloudflare 可达 · 源站 Web 未测试”。公开域名成功只证明用户网站路径可用，不得据此声称这台服务器上的源站服务健康。

服务器行的综合结果汇总用户启用的检查目标，不等于“整台服务器健康”。在 Cloudflare 分支中，公开域名结果可以计入“关联公开网站”这一用户目标，但不得写成“服务器 Web 端点成功”；源站 Web 始终单列为“未测试”。

### 11.3 HTTP 80

以下规则只用于“观察到直达已登记服务器”的快速体检，或用户手动触发的源站直连；Cloudflare 快速分支不得自动执行：

- 连接服务器 IP 的 `80`；
- 有主要域名时使用该域名作为 Host；
- 记录 TCP 与 HTTP 状态；
- `301/302/307/308` 跳转 HTTPS 属于健康行为；
- `80` 关闭但 `443` 正常时，服务器网站连通性主结果仍为“链路可达”，HTTP 仅显示辅助提示；
- `80` 的变化可以展示，但不单独制造整台服务器异常。

### 11.4 HTTPS 443

以下规则只用于“观察到直达已登记服务器”的快速体检，或用户手动触发的源站直连；Cloudflare 快速分支不得自动执行：

- 连接服务器 IP 的 `443`；
- 有主要域名时使用正确 SNI 与 Host；
- 验证公有信任链、hostname 和有效期；
- 发送受限的 `GET /` 并记录 HTTP 状态；
- 无主要域名且 TLS 握手成功时，显示“链路可达 · 身份未验证 · 无需关注”；证书只作证据展示，不执行 hostname 身份断言；
- 无主要域名、TCP 成功但 TLS 握手失败时，显示“无法判断 · 可能需要域名/SNI”，建议补充主要域名，不把它判为 IP 整体不可达；
- 有主要域名、TCP 成功但 TLS 失败时，将问题定位在 TLS/SNI 或服务器配置层，不判为 IP 整体不可达。

### 11.5 多端口综合判断

- SSH、HTTP、HTTPS 均超时：显示“多个预期端点持续超时，疑似路径或目标侧丢弃，原因未明”；
- SSH 服务响应而网站失败：IP 并非整体不可达，优先检查 Web/TLS/SNI；
- 网站链路可达而 SSH 失败：公网网站结论不受影响，单独提示 SSH 服务；
- 任一端口明确拒绝：说明至少有返回路径，不使用“IP 被整体阻断”；
- V1 不输出“中国大陆防火墙已阻断该 IP”。

## 12. 域名与服务器关联

### 12.1 自动观察公网路径

用户不需要手动选择“直连”或“Cloudflare 代理”。应用以本轮 macOS 系统解析得到、用于当前公开访问的候选集合为分类依据，参考解析只作为对照，不能覆盖当前路径事实。系统候选不完整或与参考证据存在无法归一化的实质冲突时降级为“未确认”。应用按地址族描述当前观察到的公网路径，而不声称确认了 Cloudflare 控制台配置：

#### 观察到直达已登记服务器

- 每个适用地址族的完整候选集合都只包含该资产已登记的服务器 IP；
- 只要任一适用候选是未登记 IP，即使它与服务器位于同一 ASN、云厂商或网络类别，也不能把整个域名归为直达该服务器；
- 网站公开路径与服务器直连路径可形成一致性对照；
- 域名不再指向该服务器时，显示“关联域名当前未指向该服务器”，不直接判为故障原因。

#### 观察到经 Cloudflare 边缘

- 域名解析到已知 Cloudflare 边缘地址类别；
- 同一地址族的相关候选均可安全归入 Cloudflare 边缘类别；
- 公开网站路径通过域名正常检测；
- 服务器 SSH 仍通过配置 IP 独立检测；
- 默认不把本地无法直连源站 `80/443` 视为异常。

#### 未确认

- 解析结果既不包含服务器 IP，也无法安全归入 Cloudflare 边缘类别；
- IPv4 与 IPv6 落入不同类别，同一候选集合同时包含已登记与未登记 IP，或候选集合无法完整取得时，显示“混合路径/关联关系未确认”；
- 若本次实际连接恰好命中已登记 IP，只能显示“本次连接直达该服务器”；在候选集合仍混合时，不把它提升为整个域名的直达分类；
- 显示原始事实并标记“关联关系未确认”；
- 不自动把未知 CDN、负载均衡或 GeoDNS 差异判为配置错误。

### 12.2 源站直连

Cloudflare 代理场景下，“测试源站直连”只作为按需深度动作：

- 源站可能只允许 Cloudflare IP；
- 源站可能使用 Cloudflare Origin CA；
- 源站公网直连失败可能是预期安全策略；
- 因此源站直连结果只展示证据，不影响公开网站主结论，除非用户未来显式配置“源站应可直连”。

### 12.3 Cloudflare 识别边界

- 只判断结果 IP 是否属于版本化的 Cloudflare 官方网络范围；
- 命中官方常规网段只能推断当前请求先到 Cloudflare 边缘；未命中不能绝对证明没有代理；
- 不要求不同 resolver 返回相同 Anycast IP；
- 同属 Cloudflare 正常网络类别时，不因字符串差异报异常；
- 不尝试识别 Pages、Workers、Tunnel 或具体后端产品；
- Cloudflare IP 范围必须记录来源、版本与更新时间；
- 数据新鲜度不足时降低置信度，不静默使用过期真值。

## 13. 结果模型

### 13.1 检测状态

检测状态先回答“这个资产是否已有适用于当前配置的结果”，与连通性主结果分开：

- **待首次检测**：新增资产尚未完成过“检测全部”；
- **配置已变更，待检测**：关键配置已变化，旧观测不再适用；
- **检测中**：当前批次正在处理；
- **已完成**：当前配置已有最近观测摘要，可以展示连通性主结果；
- **本批次已取消**：只在当前页面临时显示，不覆盖此前正式状态。

“待首次检测”和“配置已变更，待检测”不伪造连通性主结果，也不计入链路可达/部分可达等正式结果分布。汇总必须把资产总数拆成“已有正式结果 + 待检测”，确保计数相加等于当前资产总数。

添加、删除或修改资产后，汇总只重算当前资产的“已有正式结果/待检测”覆盖计数；不改写未变资产的正式结果和比较基线。撤销删除时恢复该资产原有摘要。

### 13.2 连通性主结果

主结果只回答网络与协议链路是否建立，不替用户推断业务内容是否正确：

- **链路可达**：关键预期端点完成相应协议层验证；HTTP 状态另行展示；
- **部分可达**：至少一个关键端点或地址族可达，但其他具备本机检测条件的预期端点在 TCP、TLS/SNI、证书或协议层失败；
- **未建立服务链路**：所有预期关键端点都未完成对应协议链路；具体证据必须继续区分超时、无路由、连接被拒绝和协议失败，不暗示整个 IP 网络路径都不可达；
- **未确认 Web 入口**：本工具未从 A/AAAA/CNAME 或可识别的 HTTPS AliasMode 获得可用 Web 地址；这是中性事实，不自动称为正常或异常；
- **无法判断**：关键探测条件或证据不足，无法安全给出连通性结论。

### 13.3 当前关注状态

- **无需关注**：链路可达且没有高优先级服务响应问题；首次即“未确认 Web 入口”，或比较基线已是中性的“未确认 Web 入口”，也属于无需关注；
- **需关注**：部分可达、未建立服务链路、证书身份失败、HTTP 5xx、HTTP 408/421/425/429/451、已登记关联关系失效，或原本存在的 Web 入口消失；Web 入口持续缺失时保留这一关注原因，直到入口恢复或用户修改资产配置；
- **本次无法判断**：连通性主结果为“无法判断”，应支持重测，但不自动算作新增异常。

所有 HTTP 4xx/5xx 都证明 Web 服务已响应。未单列的稳定 4xx 只展示状态码；HTTP 5xx 和已单列的受限状态显示“链路可达 · HTTP 状态 · 服务需关注”，原因标签保持在 HTTP 层，不得写成网络不可达。

上述 HTTP 关注规则作用于域名公开网站路径或当前主要网站路径。服务器 `80` 在 `443` 健康时是辅助端点；其 5xx/4xx 单独展示并可形成“状态变化”，但不单独把整台服务器设为“需关注”。

### 13.4 原因标签

主结果之外可附加一个或多个标签：

- 系统/本地解析路径；
- IPv4；
- IPv6；
- TCP；
- TLS/SNI；
- HTTP；
- SSH；
- 关联配置；
- 参考服务不可用；
- 原因未明。

### 13.5 置信度与证据完整度

- 置信度：高 / 中 / 低；
- 证据完整度独立展示，例如“1 个参考 resolver 不可用”；
- 资产当前链路可达但参考证据不完整时，不应被“无法判断”覆盖；
- HTTP-only 或无 hostname 的 TLS 结果缺少可验证身份，置信度不得标为“高”；
- 结论必须列出触发证据和被排除/未排除的主要替代解释。

### 13.6 变化状态

变化状态与主结果独立：

- 首次检测；
- 新增异常；
- 已恢复；
- 持续异常；
- 状态变化，例如“新增 Web 入口”；
- 无变化；
- 本次无法比较；
- 配置已变更，无法直接比较。

变化比较使用粗粒度语义。每个资产的比较指纹只包含连通性主结果、当前关注状态及关注原因、预期服务端点类别、地址族结果、HTTP 状态码类别、TLS 身份结果和公网路径类别；HTTP-only 资产另含规范化地址指纹。不比较 TTL 递减、记录顺序、耗时小幅波动、单个 Anycast IP 字符串或正常 Cloudflare Anycast IP 轮换。

变化状态按“当前关注状态 + 粗粒度连通性状态”映射：

- 无需关注 → 需关注：新增异常；
- 需关注 → 无需关注：已恢复；
- 需关注 → 需关注：持续异常；
- 无需关注 → 无需关注，但粗粒度状态发生中性变化：状态变化；
- 本次无法判断：本次无法比较；
- 比较基线为链路可达、本轮未确认 Web 入口：记录关注原因“Web 入口消失”，进入新增异常；
- 比较基线已带“Web 入口消失”关注原因、本轮仍未确认 Web 入口：保留该原因并显示持续异常；
- 比较基线已带“Web 入口消失”关注原因、本轮链路可达：显示已恢复；
- 比较基线是中性的未确认 Web 入口、本轮链路可达：显示“状态变化 · 新增 Web 入口”，不冒充故障恢复；
- HTTP 2xx/3xx/4xx 类别发生变化但链路仍可达：至少显示醒目的“状态变化”；进入 5xx 或 408/421/425/429/451 时另按“需关注”处理。

只有“检测全部”推进例行比较基线。单项重测、“重测待复核项”和手动深度诊断都属于临时复核：它们为对应行增加“临时复核结果”，但不推进基线，也不改写最近一次完整批次的正式结果。“待复核项”只包含正式批次中当前关注状态为“需关注”或“本次无法判断”的资产。

临时复核之后：

- 顶部正式汇总、筛选计数和排序继续代表最近一次完整“检测全部”，不被局部结果重算；
- 另显示一条临时摘要，例如“临时复核 3 项：2 项已恢复，1 项仍需关注”；
- 行内同时保留正式结果和带时间的临时覆盖层，避免“行已恢复、顶部仍报异常”却没有解释；
- 下一次“检测全部”开始时清除临时覆盖层；应用退出后也不保存临时结果。

“检测全部”正常到达完成事件后，正式结果以一个批次原子提交，并为每个资产维护两个粗粒度记录：

- **最近观测摘要**：保存该完整批次的终态和 `observed_at`，包括“无法判断”，供重新打开应用后展示；
- **比较基线摘要**：只在资产得到可比较的有效结果时更新，并保存 `baseline_observed_at`；当前为“无法判断”时保留该资产更早的有效基线；
- 全局另存最近一次完整批次时间，顶部正式汇总由同一批最近观测摘要生成；
- 用户取消、应用退出或批次中断时，两个记录都不提交；
- 新增资产没有比较基线，显示“首次检测”；
- hostname、IP、端口、启用服务或主要域名等关键配置变化后清除该资产旧比较基线，并把旧观测标为不再适用；下一次有效结果显示“配置已变更，无法直接比较”，而不是“首次检测”；仅修改备注名不受影响；
- 删除资产时一并删除两个摘要，撤销删除时恢复。

因此，即使某资产在最近完整批次中“无法判断”，重新打开后仍显示这次无法判断及其真实时间；详情同时显示用于下次比较的较早基线时间，不把旧“链路可达”伪装成最新结果。

### 13.7 DNS 归因原则

不再使用“满足至少两个证据”机械投票。

只有同时满足以下因果链，才可显示“高可信本地解析路径异常”：

1. 系统/本地候选与两个独立参考结果存在实质且无法归一化的冲突；
2. 快速体检第一跳实际使用本地候选并失败，且失败发生在收到原 hostname 合法 HTTP 响应之前；
3. 成对复核中，同地址族本地候选控制继续失败，而参考候选在仅改变拨号 IP、保持相同 Host/SNI/证书验证后成功；
4. 已尽可能排除 Cloudflare/GeoDNS/CDN 合法差异；
5. 关键参考服务本身健康。

“DNS 污染”只能作为可能原因出现在解释中，不作为 V1 的确定性状态名称。

### 13.8 IP/跨境归因原则

当前 Mac 的单点观测只能证明当前网络到特定服务端点的行为。

- 单次超时不等于 IP 被阻断；
- 多端口超时仍可能来自安全组、服务器防火墙、宕机、云厂商清洗或路由故障；
- 没有境外对照、多大陆运营商或服务端抓包时，不归因为 GFW；
- V1 统一使用“当前网络连接超时，原因未明”等事实性措辞。

### 13.9 下一步建议映射

每个“需关注”或“本次无法判断”资产默认只给一个最相关的下一步，其他选项放入详情。建议必须对应已观察到的证据：

| 关键证据 | 默认下一步 |
| --- | --- |
| 高可信本地解析路径异常 | 切换到手机热点后重测；若恢复，再检查当前网络的 DNS/resolver 配置 |
| 只有 IPv6 失败 | 核对 AAAA 指向、服务器 IPv6 路由与防火墙；IPv4 结果不受影响 |
| 端口明确拒绝连接 | 检查目标服务是否监听该端口，以及云安全组/主机防火墙规则 |
| 多个预期端点持续超时 | 先从云厂商控制台确认服务器运行与安全组，再换一个本地网络重测 |
| TCP 成功但 SSH identification 异常 | 确认该端口运行的是 SSH，并检查 SSH 服务日志 |
| TLS/SNI 或证书身份失败 | 核对关联域名、证书覆盖范围与服务器虚拟主机配置 |
| HTTP 5xx | 查看网站或反向代理日志；网络链路已经建立，无需先改 DNS |
| 参考 resolver 不可用 | 稍后重测；当前资产结论若已有充分证据则保持不变 |
| 关联关系未确认 | 检查域名当前 DNS 配置；工具不会自动改动记录 |

建议不得要求用户先理解 resolver、SNI 等术语；主界面使用自然语言，技术名词放在证据详情中。

## 15. 本地持久化与隐私

### 15.1 默认保存

V1 仅本地保存：

- 资产配置；
- 最近一次完整检测时间；
- 每个资产的最近观测摘要与 `observed_at`；
- 每个资产的比较基线摘要与 `baseline_observed_at`；
- 应用必要设置与数据版本。

最近观测摘要只包含连通性主结果、当前关注状态及原因、变化状态、粗粒度标签和观测时间；比较基线摘要只包含比较指纹、持续关注原因和基线时间。两者都不包含原始 DNS 报文、完整证书、HTTP 响应体或详细时序。

只有正常完成的“检测全部”批次才按资产原子提交新的最近观测摘要，并按有效性更新比较基线摘要；单项重测、“重测待复核项”、手动深度诊断和未完成批次可以在当前页面查看，但不持久化。

### 15.2 默认不保存

- 完整 DNS 原始报文；
- 完整 TLS/HTTP/SSH 诊断记录；
- 多轮历史和趋势；
- 用户浏览器数据；
- 任何账号凭据、SSH 密钥或 Cloudflare token。

本轮完整结果只保存在内存，应用退出后丢弃。用户主动复制的摘要不受此限制。

### 15.3 存储要求

- 使用 macOS Application Support 下的应用专属目录；
- 文件权限仅当前用户可读写；
- 原子写入，崩溃不得破坏资产清单；
- 不依赖浏览器 `localStorage`；
- UI 提供清除本地数据；
- 状态文件损坏时保守恢复资产配置，无法恢复则清晰提示，不静默重置。

### 15.4 网络隐私说明

准确文案应为：

> 资产与结果不会发送到 ReachRun 自建服务器或集中存储。检测过程中，域名查询会发送给当前 DNS 和所选参考 DNS/DoH 服务商，网站与服务器探测会直接连接对应目标。

## 16. 安全要求

### 16.1 本地服务

- 只监听 `tcp4` 的 `127.0.0.1:0`；
- 浏览器只打开字面量 `127.0.0.1`，不使用 `localhost`；
- 每次启动生成至少 128 bit 随机会话 token；
- token 通过 URL fragment 交给页面，不进入服务端访问日志或 Referer；
- API 请求使用 Authorization header；
- 所有请求严格校验精确 Host；有 Origin 时必须与本地页面精确一致，所有状态变更 POST/PUT 必须要求正确 Origin；
- 严格校验请求方法；所有带请求体的 API 只接受 JSON，并校验 `Content-Type: application/json`；
- 不返回允许外部来源的 CORS 头；
- 设置 `Referrer-Policy: no-referrer` 与 `Cache-Control: no-store`；
- 设置 `X-Content-Type-Options: nosniff`；
- 使用只允许本地静态资源与同源 API 的严格 CSP，并至少包含 `default-src 'self'`、`connect-src 'self'`、`object-src 'none'`、`base-uri 'none'` 和 `frame-ancestors 'none'`；
- 备注名、域名和所有网络返回内容都按纯文本渲染，不拼接为 HTML；
- 所有 API 接口（包括读取、heartbeat、变更、检测与退出）均要求有效 token。

### 16.2 目标限制

- 域名资产只允许规范化 hostname；
- 服务器资产只允许单个公网 IPv4/IPv6；
- 拒绝 loopback、私网、链路本地、组播、未指定、文档保留等非公网地址；
- 域名解析到非公网地址时可展示证据，但 Web 探测不得连接；
- 连接前完成解析与地址校验，随后直接拨已校验 IP，防止 DNS rebinding；
- 每次重定向重新执行同样校验；
- 唯一私网连接例外是系统明确公布的当前 DNS resolver，且只允许受控 DNS 端口与协议；
- 不执行用户拼接的 shell 命令；
- 系统命令如 `scutil` 必须使用固定路径和固定参数。

### 16.3 资源限制

- 限制资产数、请求体大小、并发、响应体读取量、重定向次数和总时长；
- 不允许 CIDR、端口范围、任意端口扫描、任意路径和自定义请求；
- 应用退出时取消所有连接并有界等待关闭；
- 参考 resolver 连续失败时启用批次级熔断，避免放大请求。

### 16.4 macOS Local Network Privacy

Apple 将“访问设备当前配置、位于局域网内的 DNS 服务器”列为 Local Network Privacy 的例外，V1 不应仅因直查当前 DNS 就主动申请局域网权限：

- Phase 0 在目标 macOS 真机验证系统配置 DNS 的 UDP/TCP 行为；
- V1 不连接其他私网目标，也不使用 Bonjour、组播或广播；
- 若实现过程中出现意外权限提示，先定位实际触发的网络操作，不用权限文案掩盖未知行为；
- 任何平台策略错误均不得被解释为域名 DNS 异常。

## 17. 技术方案

### 17.1 推荐技术栈

- 检测核心与本地服务：Go；
- UI：原生 HTML/CSS/JavaScript；
- 静态资源使用 `embed` 编译进二进制；
- V1 目标：当前 Apple Silicon Mac；
- Phase 0 使用 CLI；
- 引擎验证后包装为可双击 `.app`；
- V1 不做 Universal、Developer ID 签名和公证。

### 17.2 核心模块

- `asset`：域名、服务器与服务端点模型及校验；
- `store`：资产配置、最近观测摘要与比较基线摘要；
- `environment`：接口、resolver 与代理迹象；
- `systemlookup`：macOS 系统解析路径；
- `dnsquery`：受控 UDP/TCP/DoH 适配器；
- `webprobe`：系统路径、强制 IP、TLS/SNI 与 HTTP；
- `serverprobe`：SSH identification 与服务器服务端点；
- `verdict`：纯证据聚合与结论；
- `change`：当前结果与比较基线的粗粒度对比；
- `localserver`：本地 API、会话与静态 UI。

核心检查接口保持简单：

```text
RunCheck(ctx, request, emitEvent) error
```

### 17.3 本地 API

建议最小接口：

- `GET /api/state`：资产、最近观测摘要、比较基线摘要和环境概览；
- `PUT /api/assets`：保存规范化资产配置；存在活动检测时返回 `409 Conflict`；
- `POST /api/check`：基于当前配置版本的不可变快照执行，接收 JSON 检测请求并返回 NDJSON 流；已有活动检测时返回 `409 Conflict`；
- `POST /api/heartbeat`：以空 JSON 对象 `{}` 刷新已认证页面会话活跃时间并返回 `204`；
- `POST /api/shutdown`：接收空 JSON 对象 `{}` 并安全退出应用。

取消检测由浏览器中止当前 `fetch` 流并传播到 Go context，不再建设 job-id、WebSocket、独立 cancel、events 和 report 接口。

页面有焦点与否都不改变会话语义：只要页面仍打开，就按固定间隔发送 heartbeat；进程仅在没有活动检测、且超过空闲阈值未收到任何已认证页面请求或 heartbeat 后退出。heartbeat 不携带资产、结果或环境信息。

### 17.4 macOS 系统解析

Phase 0 必须验证 Go 在目标 macOS 上确实使用预期的系统解析路径。不得把 `/etc/resolv.conf` 当作 macOS 唯一真相。

推荐分层：

- `net.DefaultResolver`/原生 resolver 观察应用实际结果；
- 构建与运行时验证没有因 `netgo` 等配置绕过 macOS 原生多 resolver 路径；
- `scutil --dns` 仅作 best-effort 配置快照；
- 原始 DNS 查询使用明确指定的 resolver；
- 如标准 Go 路径不足，再评估最薄的 macOS 平台适配，不在验证前引入 Swift/cgo 大模块。

## 18. 性能与可靠性

- 健康资产快速体检与异常深度诊断使用不同队列；
- 默认域名并发目标 6～10，服务器端点并发单独受限；
- 首批结果目标 3 秒内；
- 30 个健康域名快速体检目标约 10 秒；
- 单 DNS 请求超时目标 2～4 秒；
- 单 TCP/TLS/HTTP 尝试超时目标 4～8 秒；
- 异常批次必须有总 deadline，建议 30～45 秒，最终值由 Spike 决定；
- 同一参考 resolver 连续失败时显示“参考服务不可用”并熔断；
- 用户停止、刷新或退出时立即取消在途工作；
- 单个资产崩溃或超时不得影响其他资产；
- 所有 goroutine、连接和响应体必须有关闭路径。

## 19. Phase 0：网络能力 Spike

正式 UI 前先用最小 CLI 验证证据是否可靠。

### 19.1 域名能力

5. 异常条件下 TCP DNS；

7. 强制候选 IP + 正确 Host/SNI/证书验证；
8. IPv4/IPv6 分开检测；
9. Cloudflare 地址类别归一化；
10. HTTP 状态与安全重定向。

### 19.2 服务器能力

1. SSH TCP 建连与 identification 交换；
2. HTTP 80 与跳转；
3. HTTPS 443 + hostname/SNI；

6. IPv4/IPv6 服务器端点；
7. 当前 Mac 缺少 IPv6 路由时的安全降级；
8. 失败重试与批次取消。

### 19.3 场景矩阵

至少覆盖：

- 正常 Cloudflare Proxied 双栈域名；
- Cloudflare DNS Only/直连域名；
- NOERROR/NODATA；
- NXDOMAIN；
- 仅通过 HTTPS/SVCB AliasMode 指向可用 Web 入口；
- 多层 HTTPS/SVCB AliasMode、AliasMode 循环和仅含未支持 ServiceMode 参数；
- 错误 A；
- 正常 A + 不可达 AAAA；
- 同一地址族多个候选中一部分成功、一部分失败；
- TLS 证书错误；
- HTTP 403/404/5xx；
- 本地结果与参考解析不一致；
- 默认失败、同地址族强制候选成功；
- SSH 返回合法 identification；
- SSH 端口关闭；
- 多端口受控丢弃；
- HTTP 跳转 HTTPS；
- 原 hostname 返回重定向、后续目标超时；
- TLS/SNI 配置错误；
- Cloudflare 公开网站正常但源站不允许直连；
- 配置服务器 IPv6、但当前 Mac 没有可用 IPv6 路由；
- VPN/TUN 开启与关闭；
- 当前配置 DNS 为局域网地址时的真实行为。

关键场景至少重复 3 轮，避免把暂态网络波动写成固定规则。

### 19.4 Spike 通过标准

- 正常 Cloudflare 域名连续 3 轮不误报；
- NXDOMAIN 与 NODATA 分开；
- 坏 AAAA 不掩盖 IPv4 可用；
- 同一地址族只有全部候选完成并全部失败时才判该族失败；
- 成对的本地/参考候选复核只改变目标 IP，不复用旧连接；
- SSH identification 能稳定区分 SSH 协议端点响应与仅端口可达；
- 80 关闭、443 正常不会把网站判为“未建立服务链路”；
- 可识别的 HTTPS/SVCB AliasMode 能正确找到 Web 入口；
- 多层 AliasMode 按同一 resolver 的 `HTTPS → HTTPS → A/AAAA` 顺序解析，并保持原域名身份；
- Cloudflare 源站不可直连不会影响公开网站结论；
- 当前配置 DNS 与参考 resolver 失败都能安全降级；
- 所有无法排除 GeoDNS/CDN/目标侧故障的情况落入克制结论。

## 21. 验收标准

### 21.1 资产与日常流程

- 首次添加 30 个域名和多台服务器后可正常保存；
- 重新打开应用无需重新输入；
- 服务器未启用 SSH 和网站中的任何一项时无法保存；
- 新增资产显示“待首次检测”，关键配置变化显示“配置已变更，待检测”；汇总中的已有结果数与待检测数之和等于资产总数；
- 检测期间资产编辑被锁定，直接调用保存 API 返回 `409`；配置版本变化时旧批次结果不得提交；
- 点击一次即可检测全部；
- 点击“停止检测”会取消在途请求，不提交最近观测摘要或比较基线摘要；
- 首次检测、下一轮新增异常和已恢复能正确显示；
- 单项重测、“重测待复核项”和手动深度诊断只显示临时结果，不覆盖例行比较基线或正式汇总计数；
- 某资产在完整批次中“无法判断”后，重新打开仍显示该次结果与观测时间；更早的有效比较基线只在详情中明确标注，不冒充最新结果；
- 修改备注名保留比较基线；修改 hostname、IP、端口、启用服务或主要域名时重置该资产比较关系；
- 每个“需关注”或“本次无法判断”资产默认显示一个与证据对应的下一步；
- 正常资产默认折叠，异常和变化优先展示。

### 21.2 域名

- 系统解析和实际连接 IP 可见；
- 同一地址族一条候选失败、另一条成功时显示“部分候选失败”，不误报整个地址族不可达；
- HTTPS 与 HTTP-only 能区分；
- HTTP-only 显示“身份未验证”、置信度不高于中；首次或地址指纹变化时深度复核，稳定时不重复运行完整矩阵；
- HTTPS/SVCB AliasMode 使用同一 resolver 按 `HTTPS → HTTPS → A/AAAA` 继续解析，同时保持原域名 Host/SNI；循环或未支持 ServiceMode 安全降级为无法判断；
- 无 Web 记录显示“未确认 Web 入口”的中性状态；
- 所有 HTTP 4xx/5xx 在网络层均显示“链路可达”；稳定的 403/404 默认无需关注，500 与 408/421/425/429/451 显示“需关注”；
- HTTP 从 2xx/3xx 变化为 4xx 时进入醒目的“状态变化”汇总，不被折叠为普通无变化项；
- 原 hostname 第一跳返回重定向、后续目标失败时显示“部分可达 · 需关注”，且不把失败归因给原 hostname 的 DNS；
- IPv4 成功、IPv6 失败显示“部分可达”和 IPv6 标签；
- Cloudflare 不同正常 Anycast IP 不报异常；
- 高可信本地解析路径异常必须满足完整因果链；
- 参考 resolver 不可用时降级而不误报。

### 21.3 服务器

- SSH 22 成功可读取合法 identification，并明确“未测试登录”；
- 自定义单个 SSH 端口可识别 SSH identification；
- 连接拒绝、超时和 identification 异常可区分；
- HTTP 80 跳转 HTTPS 显示健康；
- 80 关闭、443 正常时网站连通性主结果仍为“链路可达”；
- 443 健康时，80 单独返回 5xx 只作为辅助端点提示，不把整台服务器设为“需关注”；
- 有关联域名时 443 使用正确 SNI 并验证证书；
- 无关联域名时不声称 HTTPS 身份正确；
- 无关联域名但 TLS 握手成功时显示“链路可达 · 身份未验证 · 无需关注”；TCP 成功但 TLS 失败时显示“无法判断 · 可能需要域名/SNI”；
- SSH 服务响应、网站失败时不显示 IP 整体不可达；
- 多端口超时不输出 GFW 确定性结论；
- 当前 Mac 没有可用 IPv6 路由时，服务器 IPv6 显示检测条件不足，不导致“部分可达”。

### 21.4 Cloudflare 关联

- 只有适用候选集合全部属于已登记服务器 IP 时才把整个域名归为直达；混合候选保持“关联关系未确认”；
- Cloudflare 代理域名的公开路径与服务器 SSH 分开显示；
- Cloudflare 公开网站成功只显示为“关联公开网站路径可达”，不写成服务器源站 Web 健康；
- 源站直连默认不参与公开网站主结论；
- 关联关系未知时显示事实而非误判。

### 21.5 安全与隐私

- 进程只监听 `127.0.0.1`；
- 无 token、错误 Host/Origin，或带请求体但不是 JSON 的 API 请求被拒绝；
- 外部网页不能触发检测或读取数据；
- 域名解析到非公网地址时不执行 Web 连接；
- 非公网服务器 IP、CIDR、端口范围和非法 hostname 被拒绝；
- 重定向无法触发私网探测；
- 当前配置 DNS 直查失败只造成局部降级；
- 资产、最近观测摘要、比较基线摘要和必要设置之外的数据不默认落盘；
- 没有数据发送到自建服务；
- 页面持续 heartbeat 时，空闲页面不会被自动退出；关闭页面且没有活动检测后，进程会在空闲阈值到达时退出；
- heartbeat 不包含资产、结果或环境信息；
- 应用退出后端口关闭。

## 22. 风险与应对

### 22.1 把不可达误判为审查

安全组、服务器防火墙、服务宕机、云厂商清洗、运营商路由和策略性阻断可能呈现相同超时。V1 只报告当前端点行为，不输出 GFW 确定性结论。

### 22.2 macOS resolver 证据有限

系统解析结果、resolver 配置和原始 DNS 查询是不同证据。数据模型允许字段缺失，并通过 Spike 验证实际能力。

### 22.3 CDN/GeoDNS 合法差异

不同 resolver 的 IP 差异可能正常。优先比较网络类别和实际可用性，不按字符串投票。

### 22.4 Cloudflare IP 范围变化

范围数据版本化并显示更新时间；无法确认新鲜度时降低置信度。

### 22.5 Cloudflare 源站策略

源站可能只允许 Cloudflare 或使用 Origin CA。源站直连默认是诊断证据，不影响公开路径结论。

### 22.6 macOS Local Network Privacy

系统当前配置的局域网 DNS 属于 Apple 说明的权限例外。Phase 0 仍需验证没有其他操作意外触发提示；若触发，应找到真实原因，不将其包装为正常产品流程。

### 22.7 浏览器 UI 生命周期

关闭标签页无法可靠关闭进程。通过明确退出、空闲退出、单实例和有界 shutdown 共同保证。

### 22.8 localhost 攻击面

恶意网页可能探测本地端口或诱导连接。使用高熵 token、精确 Host/Origin、无 CORS、严格目标地址和受控协议降低风险。

## 23. 已确定的产品决策

- 正式产品名为 `ReachRun`，只使用英文名；仓库名和终端命令统一为 `reachrun`；
- V1 是用户主动打开并点击一次的手动体检工具；
- 不做后台定时、通知和菜单栏常驻；
- 固定资产清单本地保存；
- 仅保留最近观测与比较基线两份粗粒度摘要，不建设历史数据库；
- 域名和服务器是一级资产，共用“检测全部”；
- 服务器 V1 只聚焦 SSH 与网站；
- SSH 默认 22，可配置一个自定义端口；
- 网站默认检查 80/443，443 是主要健康指标；
- 域名当前公网路径由系统自动观察并有限归类，不要求用户选择模式；
- Cloudflare 代理场景不默认把源站直连失败视为异常；
- 健康资产快速体检，异常资产自动深度诊断；
- DoH 是参考解析，不是“干净真值”；
- 最高 DNS 标签为“高可信本地解析路径异常”；
- V1 不输出“GFW 已阻断”结论；
- Phase 0 先做 Apple Silicon CLI，验证后再包装 `.app`；
- V1 不做 Universal、签名、公证和远程探针。
